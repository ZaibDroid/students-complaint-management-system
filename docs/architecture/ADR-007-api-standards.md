# ADR 007: API Standards & Contracts

## Purpose
Define a strict, uniform standard for all API requests and responses to ensure predictable integration for the Flutter mobile application and maintain a consistent developer experience.

## Problem
Inconsistent API structures (e.g., returning `{ "data": ... }` in one endpoint and `{ "user": ... }` in another, or using different pagination formats) require the mobile application to implement complex parsing logic and error handling per endpoint, significantly slowing down development and increasing bugs.

## Decision
1. **JSON Resource Wrappers:** Every successful response returning entities must utilize Laravel API Resources (`JsonResource`). Controllers never return raw Eloquent models or collections.
2. **BaseApiController Responses:** All controllers extend a `BaseApiController` containing standardized `successResponse()` and `errorResponse()` methods.
3. **Response Format:**
   - **Success:** `{ "success": true, "message": "...", "data": { ... } }`
   - **Error:** `{ "success": false, "message": "...", "errors": [ ... ] }`
4. **Validation:** All incoming HTTP data must be validated via Form Requests. If validation fails, Laravel automatically returns a `422 Unprocessable Entity` with a structured `errors` array. Controllers never call `$request->validate()`.
5. **Pagination:** Consistent configuration across all paginated endpoints using `config('pagination.x')`. Paginated endpoints automatically include standard `meta` and `links` objects generated by Laravel.
6. **Status Codes:** Strict adherence to REST semantics (200 OK, 201 Created, 204 No Content, 401 Unauthorized, 403 Forbidden, 404 Not Found, 422 Unprocessable Entity).

## Alternatives Considered
- *JSON:API Specification:* Evaluated adopting the strict JSON:API specification. Rejected because it introduces excessive boilerplate and nesting that is cumbersome for a simple first-party mobile application. A pragmatic custom envelope (`success`, `message`, `data`) provides sufficient structure without the bloat.

## Consequences
- Requires discipline to wrap every response in a Resource.
- Flutter developers only need to write a single API interceptor/parser to handle global success states, error popups, and validation errors, accelerating mobile development.
- Makes the backend highly predictable.

## Future Considerations
Enforcing OpenAPI (Swagger) generation from these standardized routes and resources to automatically generate Dart client code for the Flutter app.
